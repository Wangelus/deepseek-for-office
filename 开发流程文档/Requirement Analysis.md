# 需求分析

> **分析框架**：新体验 − 旧体验 − 迁移成本 > 0  
> **底层心法**：不是问"怎么实现"，而是问"用户还有哪些未被满足的潜在需求"

---

## 一、站在用户视角：现在写文档到底痛在哪？

### 痛点 1：写作被"打断"——上下文切换是生产力杀手

**旧体验**：用户在 Word 里写报告写到一半，遇到了问题（这个词用得对不对？这段要不要翻译？能不能帮我扩写？），于是：

1. 切到浏览器 → 打开 ChatGPT / DeepSeek / Claude
2. 复制文档里的文字 → 粘贴到聊天窗口
3. 输入提示词 → 等待回复
4. 复制 AI 回复 → 切回 Word → 粘贴
5. 发现格式全乱 → 手动调整

这不是"使用 AI 辅助写作"，这是**在两个完全不互通的空间里反复搬运文字**。每一次切换都在消耗注意力残留——研究显示，被打断后重新进入深度写作状态平均需要 **23 分钟**。对于每天需要写 3-5 份文档的知识工作者来说，这种"微中断"累积的损耗远超想象。

**核心矛盾**：AI 明明可以帮忙，但"找 AI 帮忙"这件事本身就成了一种额外的工作。

**来自真实用户的声音**：

> *"I was getting tired of copying and pasting from ChatGPT into my documents, and vice versa. It was a productivity-killing ritual."*  
> —— Yahoo Tech 用户使用 Claude for Word 后的评价 [^1]

> *"Copilot doesn't need to be smarter to avoid becoming the new Clippy. It needs to be quieter, clearer, and easier to ignore."*  
> —— TechCentral 评论文章 [^2]

---

### 痛点 2：AI 太"吵"了——工具反客为主的入侵感

微软 Copilot 的悬浮按钮被大量用户投诉"遮挡文档内容"。2025 年底推送的动态悬浮按钮在 2026 年 5 月被微软官方回调，承认**设计影响了用户体验** [^3]。

用户想要的是一句"帮我看下这段话有没有语病"，而不是一个随时可能弹出建议、替你改句子的 AI。

**用户对文档有强烈的"控制欲"**——尤其是在合同、邮件、报告、公文这类正式文档中：

- "这句话是我的，我不确定要不要改"
- "AI 改过的版本看起来流畅了，但我的意思变了吗？"
- "如果 AI 直接改了我的文档，谁来负责出错？"

数据佐证：Word 的 Agent Mode 试用量增长 52%，但新用户留存仅增长 11%——"试了但没留下" [^4]。核心原因：**用户不信任 AI 直接在文档上操作**。

---

### 痛点 3：生成内容不可靠——流畅但错误，正确但空洞

#### 3.1 "看上去对，其实是错的"

- Copilot 在 Word 中报告"格式修改已完成"但实际文档格式并未改变 [^5]
- WPS AI 被要求生成建设工程协议，反复输出《肉牛养殖合作协议》——"驴唇不对马嘴" [^6]
- 微软 Office 内置拼写/语法检查被反映 **80% 的建议语法不正确**或过于口语化，且会漏掉明显拼写错误 [^7]

#### 3.2 "AI 腔"从第一句就暴露了

AI 生成的文本通病：空洞连接词堆叠（"值得注意的是""在当今背景下""综上所述"），段落结构过于工整，缺少具体场景锚点。表面正式但实质是"正确但空" [^8]。

这在**中文公文写作**场景下是致命的——公文的每个字都有分量，"谁负责、做了什么、通过什么机制、到什么节点、有什么结果"缺一不可。

---

### 痛点 4：通用 AI 不懂中文办公的"规矩"

#### 4.1 公文写作——无人问津的刚需场景

党政公文有严格的格式规范（GB/T 9704-2012），涉及 **7 个维度的痛点** [^9][^10]：

| 维度           | 用户真实困境                                      |
| :----------- | :------------------------------------------ |
| **政策把握难**    | 政策更新快、区域差异大，AI 不知道"原则上"和"必要时"的区别            |
| **逻辑思维难**    | 公文按"背景→依据→事项→要求"展开，AI 写的常概念模糊、论证跳跃          |
| **语言表达难**    | 需要庄重准确，AI 输出要么口语化，要么空洞花哨                    |
| **格式规范繁琐**   | 标题二号小标宋、正文三号仿宋、页边距上 3.7cm 下 3.5cm——手动排版极度耗时 |
| **素材收集难**    | 历史公文、上级政策分散，找参考耗时耗力                         |
| **流程把控难**    | 拟稿→核稿→会签→签发，多层级审核，反复修改                      |
| **"AI 味"问题** | 意义膨胀、假深刻、模糊主体、规则三连、万能结论                     |

#### 4.2 投标文件——高价值但零覆盖

投标文件写作是比公文更痛的场景：
- 一稿定生死，不能出错
- 有严格的评分标准，需要在格式和内容上都"满足标书要求"
- 技术方案、商务方案、报价方案的措辞风格完全不同
- **目前市面上没有任何 AI 写作助手专门做投标文件文风**

#### 4.3 竞品现状：所有人都在做"通用英文写作助手"

| 竞品 | 定位 | 中文公文/投标支持 |
|:---|:---|:---|
| Microsoft Copilot | 通用 AI，英文优先 | ❌ 完全不支持 |
| Claude for Word | 通用写作辅助 | ❌ 英文优先，"修订模式"是亮点但无场景适配 |
| WPS AI / 灵犀 | 通用中文 AI | ⚠️ 有公文模板，但生成质量差，无投标场景 |
| OfficeAI 助手 | 模板填充 | ❌ 无 AI 能力 |
| Word-GPT-Plus | ChatGPT 侧边栏 | ❌ 纯通用 |
| **OfficeCLI** (iOfficeAI) | CLI 文档引擎（非写作助手） | ⚠️ 互补品——可读写 OOXML 全部结构，但无 AI 写作/文风能力 |

> **关于 OfficeCLI**：它是面向 AI Agent 的命令行文档操作工具（~24K GitHub Stars），直接操作 `.docx` 底层 OOXML，不需要安装 Office。它**不是写作助手竞品**，而是**潜在的底层能力补充**——当我们需要检查页边距/页眉页脚/纸张大小等 Office.js 覆盖不到的格式时，可以作为本地后端工具调用（详见 [[#痛点 7：格式检查的能力边界——及解决方案]]）。

**核心空白**：**没有人在做"中文垂直写作场景的 AI Skill 系统"**。

---

### 痛点 5：长文本处理的无力感

当前所有 AI 写作助手的通病：

- **长文本分段处理能力弱**：一篇 2 万字的报告，要么超 token 限制，要么分段处理但上下文断裂
- **无法对长文本做结构化操作**："把这 10 页的第三章单独提取出来翻译，然后对比第四章的数据做分析"——这种指令没人能做
- **总结丢失细节层级**：用户需要的是"先给一句话结论 → 三段核心要点 → 可折叠的逐段摘要"，而不是一段几百字的概述

---

### 痛点 6：格式是"最后一公里"——排版比写作更累

写完内容是 80%，调格式是剩下痛苦的 80%。用户写完文档后的典型操作：

1. 统一标题字体字号（一级标题是什么字体？二级呢？）
2. 调整段落间距、行距（前后段是不是一样的？）
3. 检查页边距是否符合要求（公文有国家标准）
4. 确认图表编号连续、交叉引用正确

这些操作**机械、耗时、易遗漏**。用户不期望 AI 替代排版，但期望 AI 能**检查并提醒**。

### 痛点 7：格式检查的能力边界——及解决方案

#### 7.1 为什么 Office.js 覆盖不全

Office.js 设计初衷是**内容级插件**而非完整文档结构操控工具。能检查的和不能检查的属性如下：

| 属性 | Office.js API | 可检查？ |
|:---|:---|:---:|
| 字体名 | `Font.name` | ✅ |
| 字号 | `Font.size` | ✅ |
| 加粗/斜体 | `Font.bold` / `Font.italic` | ✅ |
| 下划线/颜色 | `Font.underline` / `Font.color` | ✅ |
| 对齐方式 | `Paragraph.alignment` | ✅ |
| 行距 | `Paragraph.lineSpacing` | ⚠️ 只返回数值，不区分倍数/固定值 |
| 段落缩进 | `Paragraph.leftIndent` | ⚠️ 数值可读但单位不可靠，无法区分首行缩进/悬挂缩进 |
| **页边距** | `Body` 无 Section 接口 | ❌ 页边距存于 `sectPr` XML 节点，Office.js 未暴露 |
| **页眉页脚** | `Section` 对象无 `getHeader()` | ❌ 页眉页脚是独立内容流，API 未暴露 |
| **纸张大小** | 无 `Section.pageSize` | ❌ 存在于 `sectPr → pgSz`，同样不暴露 |

Office.js 能覆盖约 **60%** 的日常格式检查需求。但公文场景中最关键的页边距（上 3.7cm 下 3.5cm 左 2.8cm 右 2.6cm）恰好落在覆盖范围之外。

#### 7.2 三种可选方案对比

| 方案 | 能做什么 | 代价 |
|:---|:---|:---|
| **A. 纯 Office.js** | 60% 格式检查（字体/字号/加粗/对齐/行距） | 无额外代价，保留跨平台 |
| **B. VSTO + Open XML SDK** | 100% 完整格式检查 | 放弃 Mac/Web/移动端，用户需装 .msi，不适合分发 |
| **C. OfficeCLI 本地桥接** ⭐ | 100% 完整格式检查 + 深度 OOXML 读写 | 用户多下载一个 30MB 二进制，保留跨平台 |

#### 7.3 推荐方案：OfficeCLI 本地桥接

**架构图**：

```
┌──────────────────────────────────┐
│        Word Web Add-in           │  ← 浏览器沙箱（跨平台）
│  taskpane.js                     │
│  用户点击"完整格式检查"            │
│  → fetch("http://127.0.0.1:3000  │
│           /api/check-format")    │
└──────────────┬───────────────────┘
               │ HTTP POST（localhost）
               │ Body: { docPath: "C:\\...\\当前文档.docx" }
               ▼
┌──────────────────────────────────┐
│      Python 本地桥接服务          │  ← 基于现有 HTTPS 服务器扩展 ~30 行
│  POST /api/check-format          │
│  → subprocess.run([              │
│      "officecli", "query",       │
│      docPath, "//w:sectPr"       │
│    ])                            │
│  → 解析 OOXML → JSON             │
└──────────────┬───────────────────┘
               │ subprocess (CLI)
               ▼
┌──────────────────────────────────┐
│        OfficeCLI 二进制           │  ← 单文件，无依赖
│  直接读取 .docx 底层 OOXML        │
│  · 页边距（sectPr → pgMar）       │
│  · 页眉页脚（header/footer XML）  │
│  · 纸张大小（sectPr → pgSz）      │
│  · 段落缩进精确值                 │
└──────────────────────────────────┘
```

**为什么这个方案可行**：

| 关切点 | 回应 |
|:---|:---|
| **需要服务器吗？** | ❌ 不需要。你**现在已经每天启动一个本地 Python HTTPS 服务器**（`DEPLOY.md` 第四步），在这个脚本上加 30 行 API 路由即可，不增加任何新进程 |
| **OfficeCLI 怎么装？** | 单二进制文件，放到项目目录下即可。安装脚本自动按平台下载（Windows `.exe` / Mac `darwin` / Linux） |
| **用户多做什么？** | 零额外操作。启动体验和现在完全一样——跑一个 Python 脚本 |
| **跨平台丢了吗？** | **没有。** OfficeCLI 本身跨三大桌面平台（Windows/Mac/Linux），你的 Web Add-in 本就跨平台，桥接层是 Python（也跨平台）|
| **安全吗？** | 全部在 `localhost` 闭环——OfficeCLI 只读本地 `.docx` 文件，不联网，不上传 |
| **OfficeCLI 稳定吗？** | GitHub ~24K Stars，Apache 2.0 协议，已发布 v1.x 稳定版 |

**分阶段落地策略**：

```
Phase 2（基础格式检查）
  → 纯 Office.js 实现
  → 覆盖：字体/字号/加粗/斜体/下划线/颜色/对齐/行距
  → 不可检查的项标注"建议人工复核"

Phase 3（深度格式检查）
  → 引入 OfficeCLI 本地桥接
  → 额外覆盖：页边距/页眉页脚/纸张大小/段落缩进精确值/样式继承链
  → 实现"一键对照 GB/T 9704 公文格式标准"全量检查
```

## 二、产品思维的映射：把痛点翻译成需求假设

运用产品思维的四维框架 [^11]：

### 用户价值（定方向）

> **核心假设**：将 AI 无缝嵌入 Word 写作流，把"写→问→改"三步缩短为"写→一键操作"，用户每天节省 30-60 分钟的上下文切换和格式调整时间。

| 旧体验 | 新体验 | 迁移成本 |
|:---|:---|:---|
| 写文档 → 切浏览器 → 粘贴 → 等回复 → 切回 → 粘贴 → 调格式 | 选中文字 → 点击按钮 → AI 直接在侧边栏处理 → 一键插入 | 安装加载项（10 分钟）+ 切换使用习惯 |
| 手动逐段检查格式 → 对照标准逐项核验 | 一键格式检查 → 标注不合规项 → AI 给出修正建议 | 信任 AI 不会误报 |

**判断**：新体验 − 旧体验 − 迁移成本 > 0 成立，前提是新体验足够流畅。

### 场景思维（切细节）

| 场景 | 5W1H | 核心需求 |
|:---|:---|:---|
| 政府工作人员写通知 | 谁：科员 / 何时：下班前 / 何地：办公室 Word / 何事：起草会议通知 / 为何：下发到各科室 | 公文格式一键套用 + 政治表述自动检查 |
| 投标专员写技术方案 | 谁：商务 / 何时：截止日前 / 何地：Word / 何事：技术方案撰写 / 为何：中标 | 评分标准对应 + 技术术语一致性检查 |
| 研究生写论文 | 谁：学生 / 何时：深夜 / 何地：Word / 何事：文献综述 + 格式排版 / 为何：交稿 | 长文本分段总结 + 引用格式检查 |
| 商务人士写邮件/报告 | 谁：经理 / 何时：随时 / 何地：Word + Outlook / 何事：起草报告/邮件 / 为何：汇报/沟通 | 快速起草 + 润色 + 翻译 |

### 商业价值（算账）

| 用户角色    | LTV 估算            | 付费意愿信号                           |
| :------ | :---------------- | :------------------------------- |
| 政府/事业单位 | 高（使用频率高，场景刚需）     | 已愿意为公文模板付费（WPS 会员），对合规性检查有极高支付意愿 |
| 企业投标部门  | 极高（一单业务价值数十万到数百万） | 节省 1-2 天撰写时间 = 极高 ROI            |
| 知识工作者   | 中（需要但非刚需）         | 竞品 $20-30/月已有市场验证                |
| 学生/研究者  | 低（付费能力有限）         | 免费引流品 → 转化为口碑传播者                 |

### 增长与壁垒（看长远）

- **留存率驱动**：公文 Skill 一旦嵌入用户工作流，切换到其他竞品的成本极高（竞品没有这个 Skill）
- **网络效应**：Skill 模板可社区贡献 —— 一个用户创建的投标 Skill 被其他用户使用和改进
- **壁垒来源**：不是 AI 能力本身（DeepSeek API 任何人都能调），而是**场景化的 prompt 工程 + Skill 模板库 + 格式规则库**的积累

## 三、需求分级（MoSCoW）

### Must（没它不行——已完成 ✅）

- [x] DeepSeek API 集成到 Word 侧边栏
- [x] 选中文字 → AI 处理 → 一键插入文档
- [x] 基础文本处理：校对、起草、翻译、总结
- [x] 聊天模式 + 文档上下文感知

### Should（应该有——Phase 2 核心差异化）

- [ ] **长文本分段处理**：自动分块 + 跨段上下文保持
- [ ] **扩写/略写模式**：根据目标字数智能调整篇幅
- [ ] **文风 Skill 系统 v1**：
  - 党政公文 Skill（通知、报告、请示、函等文种模板 + 政治表述库）
  - 投标文件 Skill（技术方案 + 商务方案文风模板）
  - 学术论文 Skill（APA/国标引用格式支持）
  - 商务邮件/报告 Skill（正式/半正式/口语化多档可选）
- [ ] **基础格式检查**：字体名、字号、加粗/斜体、行距（部分）、对齐方式的自动检查与标注
- [ ] **Markdown 渲染增强**：AI 输出在侧边栏中支持表格、代码高亮

### Could（锦上添花——Phase 3 进阶）

- [ ] **Agent + Function Calling 自动操作文档**：AI 自主决定调哪个工具（改字体、插入段落、替换文本），通过 Function Calling 执行。AI 检测到用户要求"把这段改为仿宋三号"，自动调用 Office.js 修改
- [ ] **格式排版深度检查**（OfficeCLI 本地桥接）：页边距、页眉页脚、纸张大小、段落缩进精确值、样式继承链 → 实现"一键对照 GB/T 9704 公文格式标准"全量检查（技术方案见 [[#痛点 7：格式检查的能力边界——及解决方案]]）
- [ ] **Skill 市场**：用户可创建、分享、导入自定义 Skill 模板
- [ ] **批处理模式**：一次选中多个段落，批量执行不同操作
- [ ] **多模型支持**：除 DeepSeek 外，可选配通义千问、文心一言等国产模型
- [ ] **本地模型支持**：Ollama 集成，支持完全离线使用（政务场景刚需）

### Won't（明确不做——此版本砍掉）

- ❌ **VSTO/COM 加载项路线**：能拿到完整格式信息，但会丢失 Web Add-in 的跨平台优势（Mac/Web/iPad 全部失效），且分发方式从"商店部署"降级为"用户手动装 .msi"。不再考虑
- ❌ PDF 文档直接编辑（超出 Word 加载项定位）
- ❌ 多人协作 AI 辅助（过于复杂，需后端服务支持）
- ❌ 自建大模型（成本不可控，集中精力做 Skill 层）
- ❌ 移动端支持（Word Mobile 不支持 Web 加载项）

## 四、用户场景故事（需求验证素材）

### 场景 A：政府工作人员写会议通知

> 小张是某市局办公室科员，明天要发一份"关于召开全市安全生产工作会议的通知"。
> 
> **旧流程**：打开去年的会议通知模板 → 复制 → 改日期、地点、参会人员 → 对照 GB/T 9704 格式标准逐项检查（标题是不是二号小标宋？正文是不是三号仿宋？页边距对不对？）→ 发给处长审核 → 处长说"这个表述不符合最新文件精神" → 回去改 → 再发 → 反复 3 轮 → 最终发出耗时 4 小时。
> 
> **新流程（装了本加载项后）**：输入"写一份关于召开全市安全生产工作会议的通知" → 选择"党政公文 Skill" → AI 生成符合格式的初稿 → 格式检查自动标注不合规项 → 一键修正 → 处长审核时只需关注内容，不再返回格式问题 → 耗时 1 小时。

### 场景 B：投标专员赶标书

> 小王是一家系统集成公司的投标专员，本周五截止某政府项目的投标。技术方案需要写 50 页，涵盖需求分析、技术架构、实施方案、售后服务。
> 
> **旧流程**：从上个项目的标书复制框架 → 逐段改写 → 反复去 ChatGPT 问"这段话够专业吗？"→ 复制回来 → 逐条对照评分标准确认"加分项有没有都写到"→ 熬两个通宵 → 交稿时第 36 页的字体和第 12 页不统一 → 被扣分。
> 
> **新流程**：在 Word 中直接用投标 Skill → 输入项目需求文档 → AI 生成技术方案框架 → 逐段扩写/略写调整篇幅 → 一键格式一致性检查 → 评分标准对照（加分项覆盖度分析）→ 按时交付。

## 六、结论：我们做对了什么，需要纠正什么

### ✅ 对的方向

1. **嵌入 Word 而非替代 Word**：用户不想学新工具，他们想在正在使用的工具里获得 AI 能力。当前加载项架构方向正确。
2. **DeepSeek 作为底层模型**：成本低、中文能力强、支持 OpenAI 兼容接口 → 切换成本低，可接入其他兼容模型。
3. **中文垂直场景（公文/投标/学术）**：竞品空白的真正蓝海。不是"又一个 AI 写作插件"，而是"中文专业写作的 AI 技能包"。
4. **Skill 系统而非通用聊天**：用户不需要另一个 ChatGPT 在侧边栏，他们需要"一键生成符合规范的公文"。
5. **Function Calling 方向**：AI 自主调用工具操作文档是正确的终局形态，前提是基础体验先做好。

### ⚠️ 需要纠正的认知

1. **"MCP 接口"概念混淆**：MCP 是 Anthropic 的模型上下文协议，DeepSeek 不兼容。你要做的实际上是 **OpenAI Function Calling + Office.js**，让 AI 通过工具调用来操作文档。不影响实现，但面试/简历里用语要准确。
2. **格式检查的能力边界——已有解决方案**：Office.js 能覆盖 60%（字体/字号/加粗/对齐/行距），页边距/页眉页脚/纸张大小不在其范围内。但**不需要因此就走 VSTO 路线放弃跨平台**。已发现 OfficeCLI（~24K Stars，Apache 2.0）可通过本地桥接补齐剩余 40%，单二进制无依赖，不需要服务器。Phase 2 先做纯 Office.js 基础检查，Phase 3 引入 OfficeCLI 做深度检查。详见 [[#痛点 7：格式检查的能力边界——及解决方案]]。
3. **功能范围收缩**：同时做长文本 + 6 个 Skill + 格式检查 + Agent 自动操作 → 一个人做不完。按 Phase 拆分，每个 Phase 只交付一个核心增量。

### 📋 执行路线图

```
Phase 1（当前在做）   → 文本处理管线完善（扩写/略写 + 长文本分段 + 分段总结）
Phase 2（核心差异）   → 中文文风 Skill 系统（公文/投标/学术/商务）+ 基础格式检查（纯 Office.js，60% 覆盖）
Phase 3（进阶能力）   → Agent + Function Calling 自动操作文档 + 深度格式检查（OfficeCLI 本地桥接，100% 覆盖）+ Skill 市场雏形
```
